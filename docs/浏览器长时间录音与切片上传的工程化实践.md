# 浏览器长时间录音与切片上传的工程化实践

> 目标：**长时间录音（小时级）+ 稳定切片上传 + 不阻塞主线程 + 可控失败与边界处理**

本文不是 Demo，而是一套**可上线的工程方案总结**，适用于：

- Web 录音
- Electron / WebView
- 需要边录边传的场景（存储 / ASR / 审计）

---

## 一、背景问题

浏览器中使用 `MediaRecorder` 录音非常方便，但一旦进入 **长时间录音 + 实时上传**，会立刻遇到以下挑战：

- 主线程不能被阻塞
- 网络慢 / 断网
- 上传失败重试
- 内存持续增长
- 页面切后台 / 锁屏

如果只是简单在 `ondataavailable` 里 `fetch`，**一定会翻车**。

---

## 二、核心设计思想

### 1️⃣ 采集与上传彻底解耦

```
MediaRecorder
  ↓ (1s)
ondataavailable
  ↓
内存缓冲 buffer
  ↓ (≥2MB / pause / stop)
上传队列 uploadQueue
  ↓ (串行)
网络上传
```

> **采集只做内存操作，上传只在队列中发生**

---

### 2️⃣ 为什么不能直接上传？

- `fetch` 是慢 I/O
- 网络不稳定
- retry 会阻塞

👉 **必须引入队列模型（生产者 / 消费者）**

---

## 三、MediaRecorder 行为认知

```js
mediaRecorder.start(1000)
```

- `ondataavailable` **不是音频帧**
- `e.data` 是 **编码后的 Blob（时间片）**
- timeslice 决定触发频率

---

## 四、2MB 切片 ≠ 不会内存爆

### 常见误区

> 上传成功后会 shift 掉队列，为什么还会无限增长？

### 真相

- **2MB 只是单个 task 的大小**
- 队列增长取决于：

```
录音产生速度  >  上传完成速度
```

这是一个**典型的生产者-消费者失衡问题**。

---

## 五、关键实现方案

### 1️⃣ 状态与常量

```js
const UPLOAD_THRESHOLD = 2 * 1024 * 1024 // 2MB
const MAX_QUEUE_LENGTH = 20 // 队列上限
const MAX_RETRY = 3
```

---

### 2️⃣ 非阻塞采集（主线程安全）

```js
mediaRecorder.ondataavailable = (e) => {
  if (!e.data || e.data.size === 0) return

  bufferBlobs.push(e.data)
  bufferSize += e.data.size

  if (bufferSize >= UPLOAD_THRESHOLD) {
    flushBuffer("threshold")
  }
}
```

✔ 只做内存操作
✔ 无 await / 无网络

---

### 3️⃣ flush：进入上传队列（解耦核心）

```js
function flushBuffer(reason) {
  if (bufferBlobs.length === 0) return

  if (uploadQueue.length >= MAX_QUEUE_LENGTH) {
    mediaRecorder.pause()
    throw new Error("upload queue overflow")
  }

  const blob = new Blob(bufferBlobs, { type: bufferBlobs[0].type })

  uploadQueue.push({
    seq: seq++,
    blob,
    retry: 0,
    reason,
  })

  bufferBlobs = []
  bufferSize = 0

  processUploadQueue()
}
```

---

### 4️⃣ 串行上传 + 重试（防死循环）

```js
async function processUploadQueue() {
  if (uploading) return
  uploading = true

  while (uploadQueue.length > 0) {
    const task = uploadQueue[0]
    try {
      await uploadChunk(task)
      uploadQueue.shift()
    } catch (e) {
      task.retry++
      if (task.retry > MAX_RETRY) {
        mediaRecorder.stop()
        uploadQueue = []
        break
      }
      await delay(1000 * task.retry)
    }
  }

  uploading = false
}
```

---

### 5️⃣ pause / stop 时不满 2MB 也要上传

```js
function pauseRecord() {
  mediaRecorder.pause()
  flushBuffer("pause")
}

function stopRecord() {
  mediaRecorder.stop()
  flushBuffer("stop")
}
```

## 六、必须处理的边界情况（重点）

### 1️⃣ 队列无限增长（最危险）

- 网络慢 / 断网
- retry 期间持续产生数据

👉 **必须限制 uploadQueue 长度**

---

### 2️⃣ 页面切后台 / 锁屏（iOS 必踩）

```js
document.addEventListener("visibilitychange", () => {
  if (document.hidden) {
    mediaRecorder.pause()
    flushBuffer("background")
  }
})
```

---

### 3️⃣ 网络断开

```js
window.addEventListener("offline", () => {
  console.warn("network offline")
})

window.addEventListener("online", () => {
  processUploadQueue()
})
```

---

### 4️⃣ MediaRecorder 假死（无回调）

```js
let lastDataTime = Date.now()

setInterval(() => {
  if (mediaRecorder.state === "recording" && Date.now() - lastDataTime > 5000) {
    console.warn("recorder stalled")
  }
}, 3000)
```

---

### 5️⃣ 页面关闭 / 刷新

```js
window.addEventListener("beforeunload", () => {
  flushBuffer("unload")
})
```

兜底方案：`navigator.sendBeacon`

## 八、关键经验总结

> **2MB 是粒度控制，不是稳定性保障**

真正保证系统稳定的是：

- 背压（backpressure）
- 队列上限
- 网络异常处理
- 生命周期感知

## 可复用的录音切片上传控制器（工程级封装）

> 目标：为多个录音模块提供**统一、可配置、可捕获错误**的切片上传能力

### 设计目标

- 可配置切片大小（如 2MB）
- 可配置最大重试次数 / 退避策略
- 自动串行消费上传队列（防并发）
- 不阻塞主线程
- 任意一步失败，可由调用方捕获并提示用户
- 可安全 stop / pause / resume

---

## 一、核心使用方式（调用方视角）

```js
const uploader = createRecorderUploader({
  chunkSize: 2 * 1024 * 1024,
  maxRetry: 5,
  upload: async (blob) => {
    await apiUpload(blob) // 你的上传接口
  },
})

mediaRecorder.ondataavailable = (e) => {
  uploader.push(e.data)
}

// 停止录音时
await uploader.flush() // 确保剩余数据上传
```

调用方只需要：

- push 数据
- 关心 flush / error

---

## 二、核心实现（推荐直接复用）

```js
export function createRecorderUploader(options) {
  const {
    chunkSize = 2 * 1024 * 1024,
    maxRetry = 3,
    upload,
    backoff = defaultBackoff,
  } = options

  let bufferBlobs = []
  let bufferSize = 0
  let uploadQueue = []
  let uploading = false
  let stopped = false

  async function push(blob) {
    if (stopped) return

    bufferBlobs.push(blob)
    bufferSize += blob.size

    if (bufferSize >= chunkSize) {
      enqueueFlush()
    }
  }

  function enqueueFlush(force = false) {
    if (bufferSize === 0) return

    const merged = new Blob(bufferBlobs, { type: bufferBlobs[0].type })
    bufferBlobs = []
    bufferSize = 0

    uploadQueue.push({ blob: merged, retry: 0 })
    processQueue()
  }

  async function processQueue() {
    if (uploading) return
    uploading = true

    try {
      while (uploadQueue.length > 0) {
        const task = uploadQueue[0]
        try {
          await upload(task.blob)
          uploadQueue.shift()
        } catch (err) {
          task.retry++
          if (task.retry > maxRetry) {
            throw err
          }
          await backoff(task.retry)
        }
      }
    } finally {
      uploading = false
    }
  }

  async function flush() {
    stopped = true
    enqueueFlush(true)
    await processQueue()
  }

  return {
    push,
    flush,
  }
}

function defaultBackoff(retry) {
  const delay = Math.min(2 ** retry * 1000, 30000)
  return new Promise((r) => setTimeout(r, delay))
}
```

---

## 三、为什么调用方可以捕获错误？

关键点在于：

- `processQueue` 中 **抛出错误**
- `flush()` 本身是 `async`，直接 `await`

```js
try {
  await uploader.flush()
} catch (e) {
  toast("录音上传失败，请重试")
}
```

这是**工程级 Promise 传播链路**，不是事件回调。

---

## 四、这个封装解决了哪些边界问题？

- buffer 不会无限增长（达到阈值即切）
- uploadQueue 不会并发消费
- 上传失败不会死循环
- delay 不阻塞主线程
- stop 时不会丢最后一段音频
